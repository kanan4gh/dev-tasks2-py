# 要求内容

## 概要

バージョン更新(`pyproject.toml` の `version`)を add-feature の「振り返りとドキュメント更新」フェーズのチェックボックスに紐づけ、フィーチャー PR にバージョン更新を含める(Issue #49 の案A)。あわせて、PR #54 でバージョンを上げ損ねている分を 0.12.2 として本 PR で上げる。

- **関連Issue**: https://github.com/kanan4gh/dev-tasks2-py/issues/49
- **使用ハーネス**: Claude Code
- **軽量パス**: 非適用
  - 基準2(変更7ファイル)と基準3(手順書・テンプレート・AGENTS.md の方針変更)を満たさないため、通常パスとする

## パス判定

- [x] 1. 既存パターンの踏襲のみで、新しいアーキテクチャ要素・新規依存を導入しない
- [ ] 2. 変更対象が3ファイル以下(テスト除く)
- [ ] 3. 対象文書(`AGENTS.md` とハーネスアダプタの規範記述・AGENTS.md プロダクト固有層が列挙する永続ドキュメント・`docs/procedures/` の手順書とテンプレート)の更新が不要
  - **記録例外**: 該当しない(下の判定理由を参照)
- [x] 4. データ形式・API契約の破壊的変更がない

**判定理由**:

- 基準1: 満たす。新規ライブラリ・レイヤーは導入しない。既存のチェックボックス構造に1項目を足すだけである
- 基準2: 満たさない。`docs/procedures/templates/tasklist.md` / `docs/procedures/add-feature.md` / `.claude/commands/add-feature.md` / `AGENTS.md` / `docs/development-guidelines.md` / `pyproject.toml` / `uv.lock` の7ファイル
- 基準3: 満たさない。記録例外にも該当しない。**変更の実体が対象文書そのもの**であり、add-feature 手順が定める「振り返りフェーズで何をするか」という手順自体を変えるため(一覧・台帳への項目追加ではなく、手順の変更)
- 基準4: 満たす。データ形式・API契約は変わらない。既存の tasklist はチェックボックスが1つ少ないだけで、steering lint は項目数を検査しない(テストで確認する)

## 背景

add-feature で実装した機能をリリースするとき、`pyproject.toml` のバージョン更新だけがどのチェックボックスにも紐づいていない。2回続けて入れ忘れ、そのたびに更新だけの PR を出している(PR #44 → #45、PR #47 → #48)。直近の PR #54 でも同様に上げていない。

| 場所 | 現状 |
|---|---|
| `AGENTS.md`(リリース節) | 「バージョンは `pyproject.toml` の `version` フィールドを更新する」。PR マージ後の話に読める |
| `docs/procedures/templates/tasklist.md` | 振り返りの表に「適切なバージョン種別」。判断であって作業ではない |
| `docs/procedures/add-feature.md` / `.claude/commands/add-feature.md` | バージョンへの言及なし |
| `docs/development-guidelines.md`(バージョニングとリリース) | 手順1が「`version` を更新する」。どの PR で行うかは未記載 |

「マージ後に上げる」と読める記述と「機能実装コードを直接 main にコミットしない」の規範が噛み合わず、マージ後に上げると更新だけの PR が必ず要る。

## ユースケースの軸

> add-feature でリリース対象の機能を実装する人(エージェント)が、振り返りフェーズの1項目としてバージョン更新を行い、機能の PR にバージョン更新が含まれる。更新だけの PR が要らなくなる。

## 実装対象の機能

### 1. 手順書とテンプレートへのチェックボックス追加
- `docs/procedures/templates/tasklist.md` の「振り返りとドキュメント更新」フェーズに、リリース判断に従ってバージョン定義を更新する項目を足す
- `docs/procedures/add-feature.md` と `.claude/commands/add-feature.md` のステップ7に、同じ内容の手順を足す(順序契約テストは両者の同一性を要求する)

### 2. リリース節の記述の整合
- `AGENTS.md` のリリース節: バージョン更新はフィーチャー PR に含める(add-feature ステップ7)ことを明記する
- `docs/development-guidelines.md` の「バージョニングとリリース」: 手順1が「フィーチャー PR 内で」行うことを明記する

### 3. 契約テスト
- 振り返りフェーズにバージョン更新の項目があること、中立手順書と Claude アダプタのステップ7が同じ内容を持つことを `tests/procedures/` に固定する

### 4. 今回の 0.12.2 への更新
- PR #54 の修正(PATCH)分のバージョン更新を、本 PR で `0.12.1` → `0.12.2` に上げる(`uv.lock` も更新)
- 本 PR 自体は手順・文書の変更であり単独ではリリース種別を持たない(development-guidelines「純ドキュメント更新は通常、単独リリースを行わず次回リリースへ含める」)。そのため、バージョン更新は #54 の分を持ち越して含める

## 受け入れ条件

### 手順書・テンプレート
- [ ] テンプレートの振り返りフェーズに、リリースする場合は `version` を更新する項目がある
- [ ] 中立手順書と Claude アダプタのステップ7に同じ内容の手順がある
- [ ] AGENTS.md と development-guidelines.md が、バージョン更新をフィーチャー PR に含めると読める

### 契約テスト
- [ ] 上記の3箇所の記述を検査するテストがあり、記述を消すと失敗する

### バージョン
- [ ] `pyproject.toml` と `uv.lock` が 0.12.2 になっている
- [ ] ローカル品質ゲートが全緑

## 成功指標

- 次回以降の add-feature で、バージョン更新だけの追加 PR が要らなくなる(Issue #49 が Close できる)

## スコープ外

以下はこのフェーズでは実装しません:

- バージョン更新の機械的な強制(pre-PR フック・lint による検査)。まずチェックボックスで紐づけ、それでも入れ忘れが続くなら別 Issue で検討する
- `platform-harness` リポジトリへの環流(本文の「プロセス上の判断」参照)
- GitHub Release の作成(PR マージ後にユーザーが判断する)

## プロセス上の判断

- `docs/procedures/` は AGENTS.md の位置づけ上「汎用層に近い」が、バージョン定義の場所(`pyproject.toml`)は技術スタック依存である。そのため手順書は「技術スタック固有層のリリース節が定めるバージョン定義」と中立に書き、`pyproject.toml` の名指しは AGENTS.md(技術スタック固有層)と development-guidelines.md に留める。この形なら汎用層の手順書は他のスタックでも読めるため、環流の要否は本作業の後で改めて判断する(振り返りに記録する)
