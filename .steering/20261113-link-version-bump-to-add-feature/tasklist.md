## タスク管理の原則

- `active`: 作業系列が継続中。未完了を許容する
- `paused`: 意図的な中断。有効な中断記録がある場合に未完了を許容する
- `complete`: 全タスクと振り返りが完了。未完了を許容しない
- 完了・技術的スキップは実態に合わせて即時記録する
- 「今日はここまで」はスキップではなく`scripts/steering_state.py pause`で記録する
- 最終品質ゲート、コミット、G3受け入れ記録、push、PRはチェックボックスにしない

### フェーズとadd-featureステップ

チェックボックスは、消化するステップごとに排他的に分割する。ステップ5の実装ループが消化するのは実装フェーズだけである。

### 学んだこと

**技術的な学び**:

- 「判断」(振り返りの表)と「作業」(バージョン更新)を別の行にして、作業のほうを `complete` より前のステップに置くと、更新だけの PR が要らなくなる。入れ忘れの原因は、作業が手順に紐づいていなかったことだった
- 中立手順書とアダプタのステップ7は同じ行を持つ必要があり、既存の順序契約テストの仕組みに乗せると文言のずれを検知できる

**プロセス上の改善点**:

- 先に契約テストを書き、変更前の文書で4件失敗することを確認してから文書を変える順序は、文書変更でも有効だった

### 次回への改善提案

- **チェックだけ付けて更新しない可能性は残る**(コードレビューの指摘)。新チェックは「更新する」「しない場合は理由を記録する」の2択で、どちらも行わずに `[x]` にできる。次のリリース対象機能で入れ忘れが再発したら、PR 前の機械的な検査(lint)を別 Issue で検討する
- **並行 PR で版番号が衝突しうる**。単一利用者で順にマージする現状では起きにくいが、並行作業が増えたら再検討する
- **`platform-harness` への環流**: 手順書は「技術スタック固有層のリリース節が定めるバージョン定義」と中立に書いてあるため、環流の要否を `/distill` で判断する
- 「PR」と「 PR 」の表記が文書ごとに揺れている(手順書は前者、AGENTS.md とガイドラインは後者)。次に該当文書を触る機会に統一してよい
