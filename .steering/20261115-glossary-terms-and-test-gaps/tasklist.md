### 計画と実績の差分

**計画と異なった点**:

- #68 は Issue の見立て(「テストが無いだけ」)より重かった。事前に MCP の各ツールを壊れたファイルで実際に呼ぶと、28ツールのうち6ツール(`get_active_project`・`list_projects`・`get_overview`・`list_routines`・`add_routine`・`get_daily_stats`)が `ToolError`(メッセージのみ)になり、原因と対処が失われていた。テストの追加ではなく、デコレータで全ツールを包む修正にした
- デコレータの適用順は、計画の `@track @_app_errors_as_text`(整形が内側)から、`@_app_errors_as_text @track`(整形が外側)に変えた。整形が内側だと、`AppError` が整形済みのテキストとして `track` に届き、壊れたファイルの呼び出しが「成功」として記録され、`get_mcp_stats` に出なくなる(コードレビューの指摘)。外側にすると、従来どおり `AppError` が `track` に届き、失敗として記録される。そのテストも追加した
- MCP のテスト対象は28ツール中23ツール。タイマー系(`get_timer_status`・`start_timer`・`stop_timer`・`cancel_timer`)は、壊れた `timer.yaml` を「動いていない」として扱う設計で、`get_mcp_stats` は保存ファイルを読まない。全28ツールが包まれていることは、別の検査で担保した
- glossary の概況表示は、実装を読むと3つの入口で中身が揃っていなかった(CLI と MCP は「今とりかかるべきタスク」を持ち、Web はタイマーと達成率を持つ。一時停止中のルーティーンを数えるのは CLI と Web で、MCP は数えない)。定義を「共通の核 + 入口ごとの差」にした

### 学んだこと

**技術的な学び**:

- 「テストが無い」と書かれた Issue は、テストを書く前に、対象を実際に実行して確かめると、実害のある不具合が見つかることがある(今回は6ツール)。テストを先に書いて失敗を確認する手順が、そのまま修正の範囲を決めた
- 呼び出しの記録(`track`)と整形(`AppError` → テキスト)の順序は、記録の意味(成功/失敗)を変える。デコレータを足すときは、既存のデコレータとの順序が観測されるものに影響しないかを見る
- 共通部品の抽出は、「検査の強さが変わらない」を、わざと誤りを入れた文書で前後に比べて確かめると、機械的に確認できた(落ちたテスト18件が前後で一致)

**プロセス上の改善点**:

- #64・#67(前回)と同じく、Issue にまとめた小さな課題を、1つの PR で片付けられる単位にまとめると、レビューの往復が少なかった

### 次回への改善提案

- MCP の既存ツールに、`try/except AppError` が20か所残っている(デコレータと重複するが、挙動は同じ)。整理して、エラー処理の経路を1つにできる
- 概況表示の中身が入口(CLI・MCP・Web)で揃っていない(タイマーの有無、上位3件の有無、一時停止中のルーティーンの扱い)。揃えるか、差を仕様として認めるかの判断が要る
- 共通部品を `tests/procedures/_doc_currency.py` に置き、pyright の `extraPaths` に足した。テストのディレクトリを package にするほうが標準的だが、他のテストへの影響が大きいので見送った
