## タスク管理の原則

- `active`: 作業系列が継続中。未完了を許容する
- `paused`: 意図的な中断。有効な中断記録がある場合に未完了を許容する
- `complete`: 全タスクと振り返りが完了。未完了を許容しない
- 完了・技術的スキップは実態に合わせて即時記録する
- 「今日はここまで」はスキップではなく`scripts/steering_state.py pause`で記録する
- 最終品質ゲート、コミット、G3受け入れ記録、push、PRはチェックボックスにしない

### フェーズとadd-featureステップ

チェックボックスは、消化するステップごとに排他的に分割する。ステップ5の実装ループが消化するのは実装フェーズだけである。

| フェーズ | 消化するステップ |
|---|---|
| 実装フェーズ（フェーズ1〜4） | ステップ5 |
| 4段検証 | ステップ6 |
| 振り返りとドキュメント更新 | ステップ7 |
| `complete`遷移・最終品質ゲート・PR | ステップ7終端・ステップ8（手順管理） |

技術的理由でタスクが不要になった場合だけ、取り消し線と具体的理由を付けて完了扱いにする。時間や難易度を理由に使わない。

### 計画と実績の差分

**計画と異なった点**:

- 検査テストを、計画より強くした。コードレビューの指摘で、「コマンド名が本文のどこかに出ていれば通る」「オプション名を見ていない」「未実装の節より後ろに節を足すと検査をすり抜ける」の3つの穴が見つかり、(1) コマンド表の行ベース、(2) 表のオプション名を実際のコマンド定義と照合、(3) 未実装の節が最後であること、に改めた。わざと壊した文書(実在しない `list --priority` を足す・表の行を消す)で、検査が落ちることを確認した
- 検査の禁止語 `npm` を外した。Web GUI 節の現行の記述「node / npm を使わず」に一致する誤検出だったため。期待を緩めたのではなく、検査の基準が不適切だった
- `docs/glossary.md` を2行直した。見出しの変更で、glossary からのリンク(アンカー)が切れたため。変更対象は計画の `functional-design.md` + テストから、`glossary.md` が加わって3ファイルになった
- 「未実装の設計」節の範囲を、Git・GitHub 連携だけでなく「それと合わせて検討されていた一覧表示の拡張案(優先度・期限の列)」も含むと明記した。`list` の優先度/並べ替えは Git と無関係なので、実装済みの側のコマンド表に「CLI には無い」と書き、未実装の節の表からは外した

### 学んだこと

**技術的な学び**:

- 元の文書は、実装を読むと事実と違う記述が TypeScript 版由来以外にも混じっていた。例: ID の採番は「欠番を再利用しない」と書かれていたが、実装は「最大 ID + 1」で最大 ID を消すと再利用される。`daily reset` に確認プロンプトがある、`start` が Inbox で Git の案内を出す、ファイル読み込み失敗は警告つきで空データから継続する、も実装に無かった。現行化は用語の置き換えでは済まず、節ごとに実コードを読む必要があった
- 実コードを確かめた結果、実装側の既知の問題も見つかった: 壊れた YAML を読むとトレースバックになる(エラー表に「未対応」と書いた)。`task-py web --help` の説明が「(読み取り専用)」のまま。CLI の `show` が解禁日を表示しない
- 文書の検査は「文面」ではなく「存在しないものを指していないこと」(パス・コマンド・オプション)に絞ると、機械的に書けて、しかも壊れにくい

**プロセス上の改善点**:

- 元の記述を先に控えておき、移し漏れを特徴的な語の一覧で照合する方法が有効だった(Git・GitHub 連携の特徴語を照合し、欠落0件)
- 計画で「未実装の設計は消さずに隔離する」と決めておいたので、実装中に判断で迷わなかった
