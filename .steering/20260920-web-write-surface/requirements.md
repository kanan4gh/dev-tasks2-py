# 要求内容

## 概要

ローカル Web GUI の**書き込み面**を作る。ブラウザからタスクを追加・編集・状態変更・移動・削除できるようにする。1件ずつの操作に限り、競合は検出して止める。あわせて、書き込み経路に存在した**データ破損バグ3件**を前提として修正する。

- **関連Issue**: https://github.com/kanan4gh/dev-tasks2-py/issues/50
- **使用ハーネス**: Claude Code
- **軽量パス**: 非適用

## パス判定（**通常パス・軽量パスのどちらでも必ず記載する**。基準の正は add-feature 手順のステップ4）

- [ ] 1. 既存パターンの踏襲のみで、新しいアーキテクチャ要素・新規依存を導入しない
- [ ] 2. 変更対象が3ファイル以下(テスト除く)
- [ ] 3. 対象文書の更新が不要
- [x] 4. データ形式・API契約の破壊的変更がない

**判定理由**:

- 基準1: **満たさない**。HTTP の書き込み経路・CSRF 防御・楽観的ロック（`If-Match` による版の照合）という、これまでリポジトリに無かった機構を追加する。**新規の依存はゼロ**。
- 基準2: **満たさない**。新規2・変更9の計11ファイル（テスト除く）。
- 基準3: **満たさない**。`docs/product-requirements.md`（GUI の段階を「書き込み面まで実装済み」へ）/ `docs/functional-design.md`（書き込み API と競合の扱い）/ `docs/architecture.md`（CSRF 防御・プロセス構成の「書き込み」欄）/ `docs/glossary.md`（新用語）。
- 基準4: **満たす**。YAML のスキーマは不変。CLI と MCP のコマンドライン・ツール契約も不変。`update_task` に再バリデーションを入れることで「不正な値の書き込み」は弾かれるようになるが、**これは壊れていた挙動の修正**であり、正しい使い方の契約は変わらない（不正値が通っていたこと自体がバグで、通した結果そのプロジェクトが読めなくなっていた）。

4項目すべてにチェックが付かないため**通常パス**。

## G3 受け入れの要否

**不要**。`.claude/` のスキル・エージェント・コマンドの frontmatter・ファイル名・配置、`settings.json` の権限、`.claude/hooks/` のいずれも変更しない。

## 背景

#46（v0.11.0）でローカル Web GUI の読み取り面を作った。本作業はその続きで、**仕分ける操作**を GUI からできるようにする。GTD の「整理」「見直し」という GUI を作った理由そのものに到達する段階である。

### 前提として直すデータ破損バグ（実機で再現を確認済み）

書き込み面を作る前に、**同じ経路に乗っている既存の欠陥**を直す。GUI のフォームは CLI のフラグより打ち間違えやすく、そのまま載せると被害が増える。

| 欠陥 | 現状の挙動 | 原因 |
|---|---|---|
| **A. 編集で不正な値が永続化され、以後そのプロジェクトが読めなくなる** | `task-py edit 1 --due bogus` が **rc=0 で「更新しました」**と表示し `due_date: bogus` を書き込む。以後 `list` / `show` / `add` がすべてトレースバックで落ち、**手で YAML を直すまで復旧できない** | `TaskManager.update_task` の `task.model_copy(update={...})`。**pydantic v2 の `model_copy` は再バリデーションしない**ため、`due_date` の形式チェックが全編集経路で素通りする |
| **B. 存在しないプロジェクトへ move するとタスクが見えなくなる** | `task-py move 1 typo` が **rc=0 で「移動しました」**と表示。`projects/typo/tasks.yaml` にタスクは残るが、`config.yaml` に無いため `project list` にも `list --all` にも出ない | `move_task` に移動先の実在検証が無い |
| **C. バリデーション失敗がトレースバックになる** | `task-py add ""` / `schedule 1 bogus` / MCP の `add_task(due_date="bogus")` が生の `ValidationError` を出す | pydantic の `ValidationError` が `AppError` に写されていない |

A と B はどちらも **rc=0 で成功を報告しながらユーザーのデータを失わせる**。#38・#42・#46 で繰り返し直してきた「静かに別のものを書き換える」と同じクラスである。

## ユースケースの軸

**利用者がブラウザからタスクを追加・編集・状態変更・移動・削除でき、その間に CLI や Claude が同じタスクを変更していた場合は、黙って上書きせずに検出して最新を見せる。**

## 実装対象の機能

### 1. 書き込み経路の安全化（前提の修正）

- `TaskManager.update_task` が保存前に **`Task` として再バリデーション**する。失敗は `AppError`（原因と対処つき）にする
- `TaskCrudUseCase.move_task` が**移動先プロジェクトの実在を検証**する。`None`（Inbox）は常に有効
- pydantic の `ValidationError` を `AppError` に写し、CLI・MCP・Web のどれからでも分かるメッセージが出るようにする

### 2. 書き込みエンドポイント（1件ずつ）

| 操作 | エンドポイント |
|---|---|
| 追加 | `POST /api/inbox/tasks` / `POST /api/projects/{name}/tasks` |
| 編集 | `PATCH .../tasks/{id}` |
| 開始 / 完了 / アーカイブ | `POST .../tasks/{id}/start` / `/done` / `/archive` |
| 削除 | `DELETE .../tasks/{id}` |
| 移動 | `POST .../tasks/{id}/move` |

解禁日は `PATCH` に含める（CLI の `schedule` 相当）。

### 3. 競合の検出（楽観的ロック）

- 既存タスクを変える操作は **`If-Match` ヘッダで、画面が見ていた `updated_at` を送る**
- サーバは保存直前に現在の `updated_at` と照合し、食い違えば **409** を返して現在の内容を本文に載せる
- `If-Match` が無ければ **428**（前提条件が必要）
- `POST`（追加）は対象が無いので不要

### 4. CSRF 防御

- 書き込みは **`Content-Type: application/json` を必須**にする（クロスオリジンではブラウザがプリフライトを投げ、`OPTIONS` を登録していないので届かない）
- `Sec-Fetch-Site` があり `same-origin` でなければ **403**
- `Origin` があり自分のホストでなければ **403**
- トークンは持たない（サーバが状態を持たないという原則を崩さない）

### 5. 画面

- 一覧の行から開始・完了・アーカイブ
- 詳細からの編集（タイトル・説明・優先度・期限・解禁日）
- 新規追加（プロジェクトを選んで）
- 移動（実在するプロジェクトから選ぶ）
- 削除（確認を置く）
- 409 のときに「別の場所で変更されました」と伝え、最新を見せる

## 受け入れ条件

### 書き込み経路の安全化

- [ ] `task-py edit <id> --due bogus` が**保存せずに**原因と対処を示すエラーで終わる（トレースバックではない）
- [ ] 上記のあとも `list` / `show` / `add` が正常に動く（データが壊れていない）
- [ ] `task-py move <id> 存在しない名前` が**移動せずに**エラーになり、`projects/<名前>/` を作らない
- [ ] `task-py add ""` / `task-py schedule <id> bogus` がトレースバックにならない
- [ ] MCP の `add_task(due_date="bogus")` がトレースバックにならない
- [ ] CLI・MCP の**正常系の挙動は一切変わらない**（既存テストが無変更で通る）

### 書き込みエンドポイント

- [ ] 追加・編集・開始・完了・アーカイブ・削除・移動がそれぞれ動き、`~/.task-py/` に反映される
- [ ] 操作対象は**常にパスで明示**され、グローバルのアクティブプロジェクトに影響されない
- [ ] 存在しないタスク・プロジェクトは 404
- [ ] 不正な値（日付形式・優先度・空タイトル）は 400 で、原因と対処を返す
- [ ] 移動先に存在しないプロジェクトを指定すると 404

### 競合の検出

- [ ] `If-Match` が現在の `updated_at` と一致すれば成功する
- [ ] 食い違えば 409 を返し、**本文に現在のタスクを載せる**（画面が最新を出せる）
- [ ] `If-Match` が無ければ 428
- [ ] **タイマーの停止で作業セッションが追記されても 409 にならない**（`append_work_session` は `updated_at` を動かさないため。編集と競合していないものを競合と呼ばない）

### CSRF 防御

- [ ] `Content-Type` が JSON でない書き込みは 415
- [ ] `Sec-Fetch-Site: cross-site` の書き込みは 403
- [ ] `Origin: http://evil.example.com` の書き込みは 403
- [ ] ヘッダが無い場合（curl・テスト）は通る。ブラウザは必ず送るため、ブラウザ経由の CSRF は塞がる
- [ ] 読み取り（`GET`）はこれらの検査を受けない

### 画面

- [ ] 実ブラウザで追加・編集・状態変更・移動・削除ができる
- [ ] 409 が起きたときに、何が起きたか分かる形で最新が出る

## 成功指標

- 段2 で**実ブラウザから実際に操作**し、`~/.task-py/` への反映と、別プロセスとの競合時の 409 を観察する
- データ破損バグ A・B について、**修正前に再現し修正後に再現しなくなる**ことを同じ手順で確認する
