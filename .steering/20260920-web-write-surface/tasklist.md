## タスク管理の原則

- `active`: 作業系列が継続中。未完了を許容する
- `paused`: 意図的な中断。有効な中断記録がある場合に未完了を許容する
- `complete`: 全タスクと振り返りが完了。未完了を許容しない
- 完了・技術的スキップは実態に合わせて即時記録する
- 「今日はここまで」はスキップではなく`scripts/steering_state.py pause`で記録する
- 最終品質ゲート、コミット、G3受け入れ記録、push、PRはチェックボックスにしない

### 計画と実績の差分

**計画と異なった点**:

- **競合検出の設計が甘かった。** design.md は「保存直前に現在の `updated_at` と照合する」としか書いておらず、実装は照合（`get_task`）と書き込みを**別々のロック区間**で行っていた。段3 で指摘され、その隙間で CLI が書くと競合検出をすり抜けて黙って上書きすることを確認した。#42 で作った再入可能ロックを使い、`TaskCrudUseCase.guarded()` で1つの排他区間にした。**「楽観的ロックを入れた」だけでは足りず、照合と書き込みの原子性まで設計に書く必要があった**
- **`If-Match` の受け入れが狭かった。** design.md は引用符つきまでしか考えていなかったが、`W/"..."`（弱い検証子）が毎回 409 になり、`*` が競合検出を無効にしていた。`*` は 428、`W/` は外して受ける形にした
- **画面の再送が、守るべき変更を巻き戻していた。** 競合のあと「最新に合わせて続ける」で再保存すると、**触っていない項目まで開いた時点の値で書き戻し**、CLI が変えたタイトルを消していた。競合の警告を見て続けても相手の変更を壊すなら、競合検出をした意味がない。フォームを開いた時点の値と比べて**利用者が実際に触った項目だけ**を送る形にした。design.md には「最新を出し直す」としか書いておらず、再送の中身までは考えていなかった
- **404 に集約していた例外を分けた。** 「開始できない」「まだ解禁されていない」「移動先が無い」がすべて 404 だった。ドメイン層に `NotFoundError` / `StateConflictError` を置いた（`AppError` のサブクラスなので CLI・MCP の表示は不変）。素の `AppError` は 404 と偽らず 500 にした
- **書き込みが入って、読み取り面のテストと画面の文言が嘘になった。** `TestReadOnly` は「全経路で全書き込みメソッドが 405」を固定しており、フッターは「読み取り専用」のままだった

**新たに必要になったタスク**:

- **ロック順の逆転によるデッドロックの修正。** 段3 指摘1 の修正（`guarded()`）が作った新しい欠陥で、ステップ7 の `doc-reviewer` が「ドキュメントの規約と実装の突き合わせ」で発見した。2つの別プロセスで再現し、`guarded()` が先にタイマーのロックを取るようにして、対照実験と恒久テストで確認した
- **データ破損バグ3件の修正（前提として同梱）。** `edit --due bogus` が rc=0 で成功を報告しながら不正値を保存し、以後そのプロジェクトが読めなくなる／`move` が存在しない移動先で rc=0 のままタスクを見えなくする／`ValidationError` がトレースバックになる。調査中に実機で再現して発見した。既存テスト3件が壊れた挙動を固定していたので書き直した

### 学んだこと

**技術的な学び**:

- **`model_copy(update=...)` は pydantic v2 で再バリデーションしない。** 編集経路でフィールドバリデータが一切効かず、不正値が保存されていた。`load()` が落ちるので、**保存後に気づいても手で YAML を直すしかない**。検証は保存の前に置く
- **楽観的ロックは「照合」と「書き込み」が同じ排他区間にあって初めて成立する。** 別々にすると、その隙間が競合検出の穴になる。今回の段3 でいちばん重い指摘だった
- **`Host` 検証は CSRF を防がない。** 攻撃者のページからの POST でも `Host` は正しい。JSON 必須でクロスオリジンにプリフライトを強制し、`OPTIONS` を登録しないのが第一層になる
- **`null` を「既定値」に読み替えると静かに壊れる。** `priority: null` が `medium` に化けて `high` が降格した。「キーが無い＝変更しない」「null＝消す」「意味を成さない null は 400」を区別する
- **版の文字列は、クライアントに返したものと同じ方法で作る。** API は pydantic の `Z`、照合は `isoformat()` の `+00:00` で、毎回かならず 409 になっていた。同じ結果を2通りの方法で作らない
- **ロックの取得順は、書いた規約を実装が守っているかをテストで縛らないと破られる。** #42 で「timer → tasks の順、逆向きは作らない」と architecture.md に書いたのは私で、#50 で自分が破った。段3 の修正（照合から書き込みまでを1つの区間に）で `guarded()` を作ったとき、その内側でタイマーを触る既存経路との入れ子ができることに気づかなかった。**「安全な修正が、別の規約を破る」**。デッドロックは症状が「ハング」なので、テストが緑のままでも起きる
- ローカルサーバでも、**書き込みを `async` にすると同期処理がイベントループを塞ぐ**。本文の読み取りだけをループ上で行い、残りを `run_in_threadpool` へ逃がす

**プロセス上の改善点**:

- **段3 が設計判断の誤りを出す、は4作業単位連続になった**（#38 8件・#42 8件・#46 7件・本作業 10件）。今回は競合検出の原子性と、再送が巻き戻す件。どちらも段1（668 tests 緑）は警告しなかった。**「書けた」と「守れている」は別**で、競合検出は特に、テストを書いても「隙間に割り込ませる」形にしないと穴が見えない
- **対照実験の価値を再確認した。** `guarded()` を素通しにすると追加したテストが落ち、戻すと通ることを確かめた。落ちなければテストは「もともと起きない事象」を確認しているだけになる
- **調査の途中で見つけた別件のバグを、成功の報告と一緒に握りつぶさなかった。** 調査のつもりで CLI の境界を叩いたら、v0.11.0 に入っている実データを壊すバグ3件が出た。GUI の話と混ぜずに、原因・影響・再現手順・「実行しないでください」を先に伝えた。ユーザーの問い（「バグは直すのですか？」）に答えて、同梱するか分けるかを選んでもらった
- **画面の座標に頼るブラウザ操作は再現性が低い。** `find` の ref と座標が混在して、同じ手順が通ったり通らなかったりし、実欠陥かブラウザ操作の失敗かの切り分けに時間を使った。**ページ内の JS を直接評価して規則を確かめる**ほうが確実だった（`toPayload` の関数本体をブラウザの JS エンジン上で評価した）
- 段2 で「フッターが『読み取り専用』のまま」を見つけられたのは、実際に画面を見たから。テストは通る
- **`doc-reviewer` は文章の校正だけでなく、ドキュメントと実装の突き合わせで実欠陥を出す。** 今回のデッドロックは、architecture.md の「逆向きは作らない」という一文を、レビュアーが実装（`guarded()` → `_release_timer` → `clear_timer_for_task`）と1行ずつ照らしたから見つかった。段3 のコードレビューは見逃していた。**ドキュメントに書いた不変条件は、レビューで実装と突き合わせる価値がある**

### 次回への改善提案

- **並行性を持つ機能の design.md に、「照合と操作が同じ排他区間か」を書く節を置く。** #42 で「`load()` から `save()` までの棚卸し」を提案したが、今回は「読んで確かめてから書く」という**アプリ層の check-then-act** で同じ穴を作った。ストレージ層だけでなく、呼び出し側が「確認してから書く」形になっている箇所を洗い出す
- **段3 の修正を入れたら、その修正が既存の規約（ロック順など）を破っていないかを確かめる。** 直したことで別の不変条件が破れる。修正後の再検証は「該当テスト」だけでなく、ドキュメントに書いた不変条件の一覧を見直す
- **クライアントが再送する内容は、design.md に書く。** 「最新を出し直す」だけでは、再送が何を送るかが決まらず、全項目を送って相手の変更を巻き戻す実装になった
- 入力検証は**データの入口ごとではなく、保存の直前の1か所**に置く。`TaskManager` に置いたので CLI・MCP・Web の3入口が同時に直った。次に入口が増えても同じ

### リリース判断

| 観点 | 評価 |

**提案**:

v0.12.0 としてリリースする。理由は2つ。

1. **v0.11.0 に入っているデータ破損バグ3件（`edit --due bogus` でプロジェクトが読めなくなる・`move` で存在しない移動先にタスクが消える・トレースバック）が直る。** GUI の書き込み面とは独立に価値があり、実データを壊しうるので、待たせる理由がない
2. GUI の書き込み面（追加・編集・状態変更・移動・削除・競合検出・CSRF 防御）が使える

リリースノートでは、**先に破損バグの修正を書く**。利用者にとっての緊急度はそちらが高い。
