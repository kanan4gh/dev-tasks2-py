# 要求内容

## 概要

GUI（ローカル Web）を載せる前に、GUI の形態と独立して存在するプロダクト側の欠落4件（`completed_at` の不在・タイマーがタスクと非接続・作業時間が記録されない・`$EDITOR` 連携の不在）を解消し、状態を YAML に外出しして別プロセスから読める土台を作る。

- **関連Issue**: https://github.com/kanan4gh/dev-tasks2-py/issues/38
- **使用ハーネス**: Claude Code
- **軽量パス**: 非適用
  - 判定結果は下の「パス判定」に記載する

## パス判定（**通常パス・軽量パスのどちらでも必ず記載する**。基準の正は add-feature 手順のステップ4）

- [ ] 1. 既存パターンの踏襲のみで、新しいアーキテクチャ要素・新規依存を導入しない
- [ ] 2. 変更対象が3ファイル以下(テスト除く)
- [ ] 3. 対象文書(`AGENTS.md` とハーネスアダプタの規範記述・AGENTS.md プロダクト固有層が列挙する永続ドキュメント・`docs/procedures/` の手順書とテンプレート)の更新が不要
- [ ] 4. データ形式・API契約の破壊的変更がない

**判定理由**（満たさない項目はその理由、記録例外を使った項目はその内容を書く）:

- 基準1: **満たさない**。新規モジュールを5つ追加する（`models/time.py` / `storage/timer_storage.py` / `services/timer_service.py` / `usecases/time_tracking_usecase.py` / `cli/editor.py`）。新規**依存**は増やさない（`click` は typer 経由で導入済み）が、タイマーという新しいドメインを既存4層すべてに通す構成の追加であり、既存パターンの踏襲だけでは済まない。
- 基準2: **満たさない**。変更対象は新規9ファイル・変更9ファイル（テスト除く）。内訳は design.md の「ディレクトリ構造」を参照。
- 基準3: **満たさない**。`docs/product-requirements.md` は「13. 作業時間の記録」を **P2（できれば）** に分類し、`docs/functional-design.md` は冒頭（10行目）で「P2（チーム機能・**作業時間記録**・テンプレート・カレンダー）は本設計書の対象外」と明記している。今回この機能を実装するため、両文書の**機能一覧・優先度分類そのものを書き換える**必要がある。これは記録例外の「一覧・台帳の項目の追加・値の更新にとどまる」に**該当しない**（機能一覧への機能追加は設計判断そのもの）。あわせて `docs/architecture.md` の永続化ストレージ表・`docs/repository-structure.md` のモジュール一覧・`docs/glossary.md` のドメイン用語も更新対象になる。
- 基準4: **満たさない**。`task-py edit <id>` をオプションなしで実行したときの挙動を、現行の「エラー終了（exit 1）」から「`$EDITOR` を起動して description を編集」へ変更する（対話端末のときのみ。非対話時は現行どおりエラー終了）。既存のフラグ駆動経路と MCP 契約は無変更だが、CLI の観測可能な挙動が変わるため破壊的変更として扱う。YAML データ形式の変更はフィールド追加のみで後方互換（旧 YAML をそのまま読める）。

4項目すべてにチェックが付く場合のみ「適用」と宣言できる。→ **4項目すべてを満たさないため通常パス**。

## 背景

2026-09-05 の壁打ちで、TaskCLI に GUI を追加する方針と、その形態を**ローカル Web**（サーバ + ブラウザ）にすることが決まった。GUI を作る理由は形態非依存で確定している:

- GTD の「整理」「見直し」が CLI / MCP のどちらでも埋まっていない唯一の穴である
- タイマー併走は CLI に**構造的に不可能**である（`cli/commands/time.py` の `time.sleep` + `rich.Live` が端末を占有する）

着手順として、**GUI の形態と独立に存在するプロダクト側の欠落を先に片付けてから GUI を載せる**方針をユーザーが選択した。本作業はその土台整備分にあたる。

土台として片付けるべき欠落は 2026-09-05 に実コードで確認済みで、本作業はそのうち4件を扱う。残る2件（undo / 操作履歴、`storage/file_storage.py` の排他制御）は別作業単位とする。

## ユースケースの軸

**ユーザーが、タスクを指定してタイマーを回すと、その作業時間がタスクに実績として残り、いつ完了したかも正確に残る。長い説明文は使い慣れたエディタ（VSCode）で書ける。そしてそれらの状態は、CLI を閉じても・別プロセス（将来のローカル Web GUI）からも同じように読める。**

## 実装対象の機能

### 1. 完了日時の記録（`completed_at`）

- `Task` に `completed_at: datetime | None` を追加し、`task-py done` で完了した時刻を記録する
- 完了後にタスクを編集しても完了日時が上書きされない（現行は `updated_at` 頼りのため上書きされる）
- アーカイブしても完了日時は保持する（アーカイブは「片付け」であり「完了」ではないため）
- 既存データ（`completed` だが `completed_at` を持たないタスク）は**バックフィルしない**。表示時に「記録なし」と出す

### 2. タイマーの永続化とタスクへの接続

- `task-py time start <duration> --task <id>` でタスクを指定してタイマーを開始できる
- タイマー状態を `~/.task-py/timer.yaml` に永続化し、**別プロセスから実行中タイマーを読める**
- 残り時間を「開始時刻 + 所要時間」から都度計算する（カウントダウン変数を持たない）。これによりプロセスが落ちても・スリープから復帰しても状態が壊れない
- `task-py time status` / `stop` / `cancel` で状態を確認・確定・破棄できる
- `--detach` でフォアグラウンド表示を伴わずにタイマーを開始できる
- 実行中タイマーは同時に1本のみ。二重起動は `AppError`（`--force` で置き換え可）

### 3. 作業時間（実績）の記録

- `Task` に作業セッション（開始・終了・秒数）の履歴を持ち、タスクごとの合計作業時間を出せる
- `task-py time stop` でタイマーの経過分がセッションとして記録される
- `task-py time log <task_id> <duration>` で手動でも実績を記録できる
- 実績の追記で `updated_at` を更新しない（時間記録は「内容の編集」ではないため）
- `task-py show` / MCP のタスク表示に合計作業時間が出る

### 4. `$EDITOR` 連携

- `task-py edit <id>` をオプションなしで実行すると `$EDITOR` が開き、description を編集できる
- `EDITOR="code --wait"` で VSCode を使える（`click.edit()` が `shlex.split` するため引数付き指定が通る）
- `--editor` / `-e` フラグでも明示的に起動できる（他のフラグと併用するため）
- 非対話端末（CI・パイプ）では現行どおりエラー終了する（エディタでハングしないため）
- 編集をキャンセル・無変更で終了した場合は正常終了（exit 0）で「変更はありませんでした」と出す

## 受け入れ条件

### 1. 完了日時の記録

- [ ] `task-py done <id>` の後、`task-py show <id>` に完了日時が表示される
- [ ] 完了後に `task-py edit <id> -t "新タイトル"` しても完了日時が変わらない
- [ ] `task-py archive <id>`（completed → archived）の後も完了日時が保持されている
- [ ] `completed_at` キーを持たない既存の `tasks.yaml` をそのまま読み込める
- [ ] 完了済みで `completed_at` を持たないタスクの表示が「記録なし」になり、`updated_at` の値が完了日時として永続化されない

### 2. タイマーの永続化とタスクへの接続

- [ ] `task-py time start 20m --task 1` でタイマーが開始し、`~/.task-py/timer.yaml` に状態が書かれる
- [ ] タイマー実行中に**別のシェル**（別プロセス）で `task-py time status` を叩くと、同じ残り時間が表示される
- [ ] タイマー実行中にプロセスを強制終了しても、次の `task-py time status` で実行中として復元される
- [ ] タイマー実行中に `task-py time start` を再実行すると `AppError` になり、`--force` で置き換えられる
- [ ] `task-py time start 20m`（`--task` なし）が現行どおり動作する（既存挙動の非破壊）
- [ ] MCP から `get_timer_status` を呼ぶと、CLI で開始したタイマーが見える

### 3. 作業時間（実績）の記録

- [ ] `task-py time start 20m --task 1` → `task-py time stop` でタスク1に作業セッションが1件記録される
- [ ] `task-py show 1` に合計作業時間とセッション数が表示される
- [ ] 作業セッションの追記で `updated_at` が変化しない
- [ ] タイマー実行中に `task-py project use <別プロジェクト>` してから `stop` しても、**開始時のプロジェクト**のタスクに記録される
- [ ] `task-py time cancel` ではセッションが記録されない
- [ ] `task-py move <id> <project>` でタスクを移動しても作業セッションが一緒に移る

### 4. `$EDITOR` 連携

- [ ] `EDITOR="code --wait" task-py edit 1` で VSCode が開き、保存して閉じると description が更新される
- [ ] エディタで変更せずに閉じると「変更はありませんでした」と出て exit 0 になる
- [ ] 改行を含む複数行の description が保存され、`task-py show 1` で読める
- [ ] 非対話端末（`echo | task-py edit 1`）では現行どおり `AppError` で exit 1 になる
- [ ] `task-py edit 1 -t "タイトル"` のようなフラグ駆動の呼び出しは一切変わらない

## 成功指標

- 上記4件がすべて実装され、`uv run python3 scripts/local_quality_gate.py` が全緑になる
- タイマー状態と作業時間が YAML から読めることで、**次の作業（ローカル Web GUI 本体）が CLI プロセスに依存せず着手できる**状態になる

## スコープ外

以下はこのフェーズでは実装しません:

- **GUI（ローカル Web）本体** — 本作業はその土台のみ
- **undo / 操作履歴** — 別作業単位（MCP 経由で LLM が一括変更する面を作るなら優先度が高いが、本作業とは独立）
- **`storage/file_storage.py` の排他制御** — `save()` が read-modify-write で lost update の余地があるが、シングルユーザの間は軽い対処でよいというユーザー判断済み。別作業単位
- **`archived_at` の追加** — アーカイブ日時が必要になったら別途追加する
- **完了 → open への再オープン遷移** — `can_transition_to()` に経路を追加しない。ただし将来追加された瞬間に `completed_at` が正しくクリアされるよう、状態変更の絞り口だけ用意する
- **`--detach` タイマーの完了通知** — デーモン化しないため、時間切れのベル通知はフォアグラウンド実行時のみ。バックグラウンド通知は GUI 側の責務
- **タイマーの複数本同時実行** — 同時1本。将来広げられるようファイル形式だけ残す
- **`task start` からのタイマー自動起動** — MCP からも呼ばれる経路に暗黙の副作用を持ち込まないため
