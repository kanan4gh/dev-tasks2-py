### 学んだこと

**技術的な学び**:

- 「このコマンドは捕捉している」という grep(`except AppError` を含まないファイルの一覧)は不十分だった。ファイル単位で見ると、同じファイル内の一部のコマンドだけが未捕捉でも見落とす。壊れたファイルを置いて全コマンドを実際に実行して初めて分かった
- 最初の全コマンド確認のシェルループは、コマンドを引用符で1語にしてしまい、全件「0」で通った(何も検査していなかった)。出力の中身を見て気づいた。確認の出力が全件同じなら、検査が空振りしていないかを疑う
- 保存ファイルの読み込みは、例外の種類ではなく「利用者が直せる情報(ファイル・行・項目)を出す」ことが目的。形の検査(最上位の型)と値の検査を分けると、文言が正確になる

**プロセス上の改善点**:

- コードレビューの指摘(未捕捉コマンド)は、計画段階で「入口で一括して扱う」方式を検討していれば避けられた。「例外の種類を増やす変更」は、その例外が届くすべての入口を数えてから計画する

### 次回への改善提案

- `shell`(対話ループ)は `except Exception` で全例外を包むため、`AppError` を専用に整形していない。壊れたファイルでは例外の文字列が出る。必要なら別 Issue で `AppError` を `render_error` で整形する
- `MCP` も `StorageReadError` を `_fmt_error` 経由で3要素に整形するが、壊れたファイルでの実行テストは無い(本作業は CLI と Web のみ)
- コマンドごとの `try/except AppError` と新デコレータが併存している。既存コマンドをデコレータへ寄せる整理は別作業にできる
