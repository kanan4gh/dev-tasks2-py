# 要求内容

## 概要

利用者に見える3つの不具合をまとめて直す。(1) `task-py web --help` が「読み取り専用」と説明している、(2) 壊れた YAML を読むとトレースバックが出て原因と対処が示されない、(3) `task-py overview` の毎日やることの案内が存在しない構文 `done r<ID>` を示している。

- **関連Issue**: https://github.com/kanan4gh/dev-tasks2-py/issues/58 , https://github.com/kanan4gh/dev-tasks2-py/issues/59 , https://github.com/kanan4gh/dev-tasks2-py/issues/60
- **使用ハーネス**: Claude Code
- **軽量パス**: 非適用
  - 基準2を満たさないため通常パス(下の「パス判定」を参照)

## パス判定（**通常パス・軽量パスのどちらでも必ず記載する**。基準の正は add-feature 手順のステップ4）

- [x] 1. 既存パターンの踏襲のみで、新しいアーキテクチャ要素・新規依存を導入しない
- [ ] 2. 変更対象が3ファイル以下(テスト除く)
- [ ] 3. 対象文書の更新が不要
- [x] 4. データ形式・API契約の破壊的変更がない

**判定理由**:

- 基準1: 満たす。`AppError` のサブクラスと、ストレージ共通の小さな読み込み補助を足すだけで、依存は増えない
- 基準2: 満たさない。`exceptions.py`・ストレージ4本(`file_storage` / `routine_storage` / `daily_log_storage` / `global_config_storage`)・新規の読み込み補助・`web.py`・`onboard.py`・`inbox.py`・Web の状態コード表で、3ファイルを超える
- 基準3: 満たさない。`docs/functional-design.md` のエラー種別表の「未対応」を「対応済み」に直す必要があり、記述そのものが変更の実体の一部になる
- 基準4: 満たす。正常に読める保存データの形式・API は変えない。壊れたファイルに対する失敗の見え方(トレースバック→3要素のエラー)が変わるのみ

**G3受け入れ**: 不要(アダプタ構成・権限・フックは変更しない)。

## 背景

#43 の現行化の中で、`task-py --help` の出力・エラー種別・`overview` の出力を実装と突き合わせて見つけた。いずれも小さいが、利用者が誤解する(#58, #60)、データが壊れたときに手がかりが無い(#59)という実害がある。

## ユースケースの軸

利用者が、(1) `--help` を読んで Web GUI が書き込めることを正しく理解し、(2) YAML が壊れたときに壊れたファイルの場所と直し方が分かり、(3) `overview` の案内をそのままコピーして実行できる。

## 実装対象の機能

### 1. web のヘルプ文(#58)
- コマンドの説明文を、読み取り専用と書かない文面にする(「127.0.0.1 のみ待ち受け」)

### 2. 壊れた保存ファイルのエラー化(#59)
- タスク・ルーティーン・日別ログ・グローバル設定の読み込みで、YAML の構文エラーと、値の検証エラーを、新しい `StorageReadError`(`AppError` のサブクラス)に包む。message は「保存先ファイルを読み込めません」、cause は対象のパスと原因(行・列を含む)、remedy は手で直すか `.bak` があればそこから戻す旨
- タイマーは現状維持(壊れても「動いていない」として扱う。状態ファイルであり、握りつぶしてもデータを失わないため)
- `overview` と `inbox` は `AppError` を捕捉していないので、捕捉して `render_error` で出す(他のコマンドは捕捉済み)
- Web は `StorageReadError` を 500 のまま原因つきで返す(状態コード表に明記)

### 3. overview の案内(#60)
- ルーティーンの案内を `task-py daily done <ID>` に直す。タスクの案内も `task-py start <ID>` / `task-py done <ID>` と、コマンド名つきの形にする

## 受け入れ条件

### web のヘルプ文
- [ ] `task-py web --help` の出力に「読み取り専用」が含まれない

### 壊れた保存ファイル
- [ ] 壊れた YAML のタスクファイルを読むと `StorageReadError` になり、cause にパスと行・列、remedy に対処が入る
- [ ] 値が不正な YAML(例: status が不明)でも同様に `StorageReadError` になる
- [ ] ルーティーン・日別ログ・グローバル設定でも同様
- [ ] `task-py list` / `overview` / `inbox` を壊れたファイルで実行すると、トレースバックではなく `[Error]` / 原因 / 対処が出て、終了コードは 1(トレースバックは出ない)
- [ ] 壊れたタイマーファイルは従来どおり「動いていない」として扱われる(回帰なし)
- [ ] Web の API は、壊れたファイルで 500 と message / cause / remedy を返す
- [ ] 正常なファイルの読み込みは変わらない(既存テストが通る)

### overview の案内
- [ ] 案内に出るコマンドが、実在するコマンドとして解決できる(`daily done`・`start`・`done` が CLI に存在し、`done r<ID>` の形が出ない)

## 成功指標

- 既存テストの全通過に加え、3件分の回帰テストが足される

## スコープ外

- 壊れたファイルの自動復旧(`.bak` からの自動復元)。案内にとどめる
- 壊れたタイマーファイルの扱いの変更
- `task-py shell` の対話ループでのエラー表示(各コマンドが `AppError` を扱う既存の仕組みに従う)
