## 起点となったAI-DLC Workflows 2.0の三層構造

議論の起点となった図は、AI-DLC Workflows 2.0を次の三層に分けていた。

1. メソドロジー層: 何を実行するか
2. 実行エンジン層: 誰が何を進めるか
3. 配布・アダプタ層: 各ハーネスでどう動かすか

### 1. メソドロジー層

`core/`に、AI-DLCのメソドロジーが定義される。

- 9種類のスコープ
  - どのステージを実行するかを決める
- 14エージェント
  - 11のドメインエキスパート
  - 2つのレビュアー
  - composer
  - 各ステージを実行するペルソナを定義する
- 5フェーズ32ステージ
  - Initialization
  - Ideation
  - Inception
  - Construction
  - Operation
- ルール、センサー、ナレッジ
  - 人間の学習を蓄積し、次回の実行へ反映する

この層が定義するのは「何を実行するか」である。

### 2. 実行エンジン層

メソドロジーを進行させる制御ループは、エンジンとコンダクターに分かれる。

#### エンジン

`aidlc-orchestrate.ts`が、状態とステージグラフから次の処理を決定論的に計算する。

- 現在の状態を読む
- 依存関係と条件を評価する
- 次に実行する処理を1件の`directive`として返す
- 進行経路の決定をLLMへ委ねない

#### コンダクター

`SKILL.md`が、エンジンの`directive`を実行する。

- 指定されたステージを実行する
- 必要なエージェントのペルソナを読み込む
- 人間へ質問する
- 成果物を作成する
- 承認ゲートで確認する
- 実行結果を`report`としてエンジンへ返す

```text
aidlc-orchestrate.ts
        │
        │ directive
        ▼
     SKILL.md
        │
        │ report
        └─────────────→ aidlc-orchestrate.ts
```

LLMはライフサイクル全体の経路を自由判断するのではなく、エンジンとのフォワーディングループを回す。

### 3. 配布・アダプタ層

`core/`の内容は、`bun scripts/package.ts`によってホストハーネスごとの配布物へ変換される。

- コンパイル
- ハーネス固有形式への変換
- 生成物のドリフトチェック
- 固有ペイロード差のアダプタによる吸収

対象となるホストハーネス:

- Claude Code
- Kiro IDE
- Kiro CLI
- Codex CLI
- opencode

Kiro CLIのように実行プロトコルやペイロード形式に差がある場合は、専用アダプタが差分を吸収する。

## uroborosへの仮対応

| AI-DLCの層 | uroborosの現在 |
|---|---|
| メソドロジー | `AGENTS.md`、`docs/procedures/`、templates |
| 実行エンジン | `add-feature`、`steering`、tasklist、Stopフック、各種lint |
| 配布・アダプタ | `.claude/`、`.agents/skills/`、`.codex/`、`.kiro/` |

表面的には同じ三層に対応させられるが、決定的な違いがある。

> AI-DLCのメソドロジーはステージグラフとしてコンパイル・実行される。uroborosのメソドロジーは、主にMarkdown正典をLLMが読んで解釈する。

### uroborosの決定論的機構

uroborosにも決定論的な機構は存在する。

- 未完了tasklistの検出
- steering構造の検査
- Issue URLや振り返りの検査
- ローカル品質ゲート
- 有料自動化経路の再混入検査
- ハーネスアダプタの構造テスト
- 環流PRの変更ファイル非重複検査

ただし、これらは主に境界検査と完了条件の強制である。

「次に何を実行するか」は、`aidlc-orchestrate.ts`のような単一の決定論的エンジンではなく、エージェントが`docs/procedures/add-feature.md`などの手順を解釈して決めている。

### 配布モデルの違い

#### AI-DLC

```text
単一のcore
  ↓ package
各ホストハーネス向け成果物
```

- 生成によって各配布物のドリフトを防止する
- ハーネス差分はmanifestやadapterへ閉じ込める

#### uroboros

```text
ハーネス中立な手順書
  ↑ 参照
各ホストハーネスの薄いラッパ
```

- 中立手順を各アダプタが参照する
- アダプタは手作業で管理される
- 構造テストと同期規約によってドリフトを検出する

### アーキテクチャ上の中心的な問い

> uroborosは「Markdown正典と薄い参照ラッパ」を維持するのか。それともメソドロジーの一部を、実行可能な決定論的エンジンへ昇格させるのか。

この問いは、軽量・通常・拡張パスの選択や、拡張パス内の検討モジュール選択を、LLMの解釈と決定論的ルールのどちらへ置くかという議論につながる。

## 「ハーネス」という用語の衝突

これまでuroborosでは、LLMを有効に動かす文脈、手順、検証、記憶の総体を「ハーネス」と呼んできた。

一方、AI-DLC Workflows 2.0では、Claude Code、Kiro、Codex、opencodeなどの実行環境を「ハーネス」と呼ぶ。

どちらも意味は通るが、同じ議論で併用すると次の二つが区別できない。

1. メソドロジーを実装・配布する仕組み全体
2. LLMを実際に動かすCLI・IDE

そのため、アーキテクチャ上の正式用語を分ける必要がある。

---

## 提案する用語体系

### 総称: AI開発ライフサイクル・フレームワーク

AI-DLC Workflowsとuroborosを総称するカテゴリとして、次を採用する案がある。

> AI開発ライフサイクル・フレームワーク<br>
> AI Development Lifecycle Framework

ハーネス中立性を強調する場合:

> ハーネス中立なAI開発プロセス・フレームワーク

このフレームワークには次が含まれる。

- メソドロジー
- プロセス実行基盤
- 状態管理
- 承認プロトコル
- 検証・ガバナンス
- ホストハーネスへの配布・アダプタ
- 学習と改善の仕組み

### 用語の階層

| 概念 | 意味 | AI-DLC | uroboros |
|---|---|---|---|
| メソドロジー | 何を、なぜ行うか | AI-DLC、5フェーズ32ステージ | SDD原則、基本フロー、steering規律 |
| ライフサイクル・フレームワーク | メソドロジーを実行・配布可能にした総体 | `aidlc-workflows` | uroboros / platform-harness |
| プロセスエンジン | 次に何を実行するか決める | `aidlc-orchestrate.ts` | 現在は主にエージェントによる手順解釈 |
| コンダクター | 指示を実行し、人間と対話する | `SKILL.md` | `add-feature`、`steering`など |
| ホストハーネス | LLMを実際に動かすCLI・IDE | Claude Code、Kiro、Codex、opencode | 同じ |
| ハーネスアダプタ | フレームワークをホスト固有形式へ投影する | `dist/claude`、`dist/codex`など | `.claude/`、`.codex/`、`.kiro/` |
| プロジェクトインスタンス | 特定プロジェクトへ適用されたフレームワーク | Space、Intent、成果物 | `docs/`、`.steering/`、実装・検証履歴 |

### 「SDDハーネス」

「SDDハーネス」は日常的な略称としては意味が通る。しかし、次の二通りに解釈できる。

1. SDDを実現する仕組み全体
2. Claude Codeなどと同列の実行ハーネス

AI-DLCとの比較では混同が起きるため、正式分類には使用しない方がよい。

### 「メタハーネス」

uroborosは複数のホストハーネスへプロセスを供給するため、相対的な役割としてはメタハーネスと呼べる。

```text
uroboros
  ├─ Claude Codeアダプタ
  ├─ Codexアダプタ
  └─ Kiroアダプタ
```

ただし、uroborosはハーネス変換だけでなく、メソドロジー、検証、知識の環流まで含む。そのため、メタハーネスは製品カテゴリではなく、アーキテクチャ上の性格を表す補助的な役割名とする。

- カテゴリ: AI開発ライフサイクル・フレームワーク
- 方法論: SDD
- アーキテクチャ上の性格: メタハーネス
- 展開先: ホストハーネス
- 展開物: ハーネスアダプタ

## uroborosの定義

議論で得られた現時点の定義:

> uroborosは、方法論としてSDDを採用し、InceptionとConstructionに焦点を当てた、ハーネス中立なAI開発ライフサイクル・フレームワークである。

より特徴を強調する場合:

> uroborosは、方法論としてSDDを採用し、InceptionとConstructionに焦点を当てた、環流型かつハーネス中立なAI開発ライフサイクル・フレームワークである。

この定義により、従来カテゴリとして使用していた「プラットフォームハーネス」を置き換えられる。

`platform-harness`という固有のリポジトリ名を変更するかどうかは別の判断とする。

### 図式化

```text
AI開発ライフサイクル・フレームワーク
├─ メソドロジーコア
│  └─ SDD原則、スコープ、手順、役割、ルール
├─ プロセス実行基盤
│  └─ 経路選択、状態、コンダクター、承認、検証
└─ ハーネス配布基盤
   └─ adapter、構造テスト、drift check
        ↓
   ホストハーネス
   ├─ Claude Code
   ├─ Kiro
   └─ Codex
```

フレームワークが個々のホストハーネスを内包するのではない。

> メソドロジーを、ホストハーネス上で実行可能な形へ投影する。

という関係である。

## 「プロジェクトハーネス」の再定義

「プラットフォームハーネス」をAI開発ライフサイクル・フレームワークへ置き換えると、「プロジェクトハーネス」にも新しい呼称が必要になる。

### アーキテクチャ上の名称

> プロジェクトライフサイクル・インスタンス<br>
> Project Lifecycle Instance

日常的には「プロジェクトインスタンス」と呼ぶ。

### インスタンスである理由

プロジェクトハーネスは単なる設定やアダプタではない。uroborosというフレームワークが、特定のプロジェクトへ具体化された実体である。

プロジェクトインスタンスには次が含まれる。

- プロダクト固有の要求、設計、用語
- 技術スタック固有の規約
- 利用するホストハーネスのアダプタ
- 個々の作業記録
- 実装・検証の履歴
- 振り返り
- distillによって抽出される知見

```text
uroboros
  = AI開発ライフサイクル・フレームワーク

各プロジェクト
  = uroborosを具体化したプロジェクトライフサイクル・インスタンス
```

### エコシステム上の役割

「インスタンス」は構造を表すが、環流元としての能動的な役割までは表さない。

環流エコシステム上では、プロジェクトインスタンスを次のように呼ぶ案がある。

> 実践ノード<br>
> Practice Node

- アーキテクチャ上: プロジェクトライフサイクル・インスタンス
- エコシステム上: 実践ノード

### 作業インスタンスとの区別

`.steering/YYYYMMDD-*/`の一件一件は、プロジェクトインスタンスではない。プロジェクト内で行われる個別の作業単位である。

AI-DLCのIntentに近い概念として、次のように呼べる。

> 作業インスタンス<br>
> Work Instance

または:

> 変更Intent<br>
> Change Intent

### 階層

```text
uroboros
AI開発ライフサイクル・フレームワーク
│
│ rollout / 適用
▼
プロジェクトライフサイクル・インスタンス
エコシステム上は「実践ノード」
│
├─ 永続コンテキスト
│  ├─ product requirements
│  ├─ functional design
│  ├─ architecture
│  └─ development guidelines
│
├─ 作業インスタンス
│  └─ .steering/YYYYMMDD-*/
│     ├─ requirements.md
│     ├─ design.md
│     └─ tasklist.md
│
├─ 実装・検証結果
│
└─ 振り返り
   │
   │ distill
   ▼
環流候補
   │
   │ 正典化・PR・release
   ▼
uroborosのフレームワーク正典
```

### 用語の置換案

| 従来の概念 | 提案する呼び方 |
|---|---|
| プラットフォームハーネス | AI開発ライフサイクル・フレームワーク |
| プラットフォームハーネスコア | フレームワーク正典／メソドロジーコア |
| プロジェクトハーネス | プロジェクトライフサイクル・インスタンス |
| エコシステム内のプロジェクト | 実践ノード |
| 個々のsteering | 作業インスタンス／変更Intent |
| distillの成果 | 環流候補／正典化候補 |
| 正典からの再展開 | rollout／下流同期 |

## 環流型エコシステム

プロジェクトインスタンスは、フレームワークの下流に配置されるだけの利用者ではない。実践を通じてフレームワークを改善する観測点・学習源でもある。

```text
フレームワーク正典
      │
      │ rollout
      ▼
プロジェクトインスタンス群
      │
      │ 実践・振り返り
      ▼
    distill
      │
      │ 普遍性・再現性・抽象性で分類
      ▼
   環流候補
      │
      │ 正典化・PR・release
      └──────────────→ フレームワーク正典
```

各プロジェクトインスタンスは、次の二つの役割を持つ。

1. フレームワークを使用して成果物を作る
2. 実践から得た知見をフレームワークへ返す

この双方向性が「実践ノード」という呼び方の理由である。

## AI-DLCとの学習ループの違い

AI-DLCにもSpace、Intent、memory、学習ループがある。そのため、プロジェクトで学習すること自体はuroboros固有ではない。

違いは学習の到達範囲と、正典へ戻す経路である。

### AI-DLC

```text
作業で得た人間の訂正
  ↓
Spaceのmemory
  ↓
同じチーム・プロジェクトの次回Intent
```

主にプロジェクト内の次回実行へ学習を反映する。

### uroboros

```text
個々の作業の振り返り
  ↓
プロジェクト内の複数作業をdistill
  ↓
プロジェクト固有知見と普遍的知見を分類
  ↓
普遍的知見をフレームワーク正典へ環流
  ↓
release
  ↓
複数のプロジェクトインスタンスへ再展開
```

uroborosの特徴:

> 個々のプロジェクトインスタンスを、フレームワークを改善する実践ノードとして扱う。

AI-DLCがプロジェクト内学習を主に扱うのに対し、uroborosは複数プロジェクトから正典へ戻し、再び複数プロジェクトへ配布する上流・下流間の学習サイクルを明示的に持つ。

この違いから、uroborosのカテゴリを次のように表現できる。

> 環流型AI開発ライフサイクル・フレームワーク

## 現時点の整理

### uroboros

> 方法論としてSDDを採用し、InceptionとConstructionに焦点を当てた、環流型かつハーネス中立なAI開発ライフサイクル・フレームワーク。

### プロジェクト

> uroborosを特定のプロダクト、技術スタック、組織制約へ具体化したプロジェクトライフサイクル・インスタンス。

### エコシステム上のプロジェクト

> 実践と振り返りを通じて環流候補を生み、フレームワーク正典の進化へ寄与する実践ノード。

### Claude Code、Kiro、Codex

> フレームワークのメソドロジーがアダプタを介して投影されるホストハーネス。
