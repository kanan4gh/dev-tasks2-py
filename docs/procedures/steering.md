# steering 手順（作業計画・実装・状態遷移・振り返り）

ステアリングファイルに基づく計画・実装・振り返りと、作業状態の遷移を管理するハーネス中立手順である。各ハーネスのスキルは本手順を参照する薄いアダプタとして実装する。

## 大原則

- `tasklist.md`を進捗と作業状態の正本とする
- 完了・技術的スキップは実態に合わせて即時記録する
- AIの各応答終了と、ステアリング作業の中断・完了を同一視しない
- 意図的な中断はタスクを偽って完了させず、`paused`と中断記録で表す
- PR・リリース対象は最終的に`complete`へ遷移し、完了プロファイルのlintを通す

## 作業状態

tasklistの先頭に固定形式で記録する。

```markdown
## 作業状態

- **状態**: active
- **状態更新日時**: 2026-07-28T10:00:00+09:00
- **使用ハーネス**: Codex
```

| 状態 | 意味 | 未完了タスク |
|---|---|---|
| `active` | 作業系列が継続中 | 許容 |
| `paused` | 意図的に中断し、再開情報を保存済み | 有効な中断記録がある場合に許容 |
| `complete` | タスクと振り返りが完了 | 許容しない |

`active`は「AIが今まさに実行中」という意味ではない。通常の応答をユーザーへ返しても`active`のままであり、「今日はここまで」「別ハーネスへ引き継ぐ」等の明示的な中断時だけ`paused`へ変更する。

状態がない旧tasklistは、未完了ゼロなら`complete`相当として後方互換で扱う。未完了がある旧tasklistは`pause`操作で状態と中断記録を追加して移行できる。

## 規律の担保

- 通常検査: `python3 scripts/steering_lint.py`
  - 全履歴の必須ファイル、Issue URL、状態整合性、中断記録、完了済み振り返りを検査する
  - `active`と正当な`paused`の未完了は違反にしない
- 完了検査: `python3 scripts/steering_lint.py --require-complete [対象]`
  - 通常規則を同じ1回の走査で評価し、指定対象だけ`complete`を要求する
- 最終ゲート: `scripts/local_quality_gate.py`
  - 既定では最新、`--steering [日付付き名]`指定時は明示対象としてsteering lintを1回実行する
  - add-featureでは別作業の新しいsteeringに影響されないよう、現在のステアリング名を必ず明示する
- GitHub Actionsは利用権限と予算がある場合だけ手動実行する任意補助経路とする

Stopフックによる応答終了ブロックは使用しない。Claude Codeの編集リマインド等、tasklist更新を促す非強制フックは併用してよい。

## ルールA: タスクが大きすぎる場合

タスクを小さなサブタスクへ分割してtasklistに追加し、1つずつ完了させる。

## ルールB: 技術的理由によるスキップ

実装方針・アーキテクチャ・依存関係の変更で不要になった場合だけ、理由と代替を記録して完了扱いにできる。

```markdown
- [x] ~~タスク名~~（実装方針変更により不要: 具体的な技術的理由）
```

「時間の都合」「今日はここまで」はスキップ理由ではない。タスクを未完了のまま`paused`へ遷移する。

## モード1: ステアリング作成

1. 現在の依頼、明示的に参照されたIssue、承認済みspecだけを要求源とする
2. `.steering/[YYYYMMDD]-[task-name]/`を作成する
3. 関連する永続ドキュメントと既存パターンを読む
4. 通常パスでは`requirements.md / design.md / tasklist.md`、軽量パスでは`requirements.md / tasklist.md`を作る
5. requirementsへIssue URL、使用ハーネス、パス判定を記録する。**通常パス・軽量パスのどちらでも**基準4項目それぞれの判定結果を記録する
6. tasklistの状態を`active`として、タイムゾーン付き日時と使用ハーネスを記録する
7. tasklistをadd-featureの消化ステップごとに排他的なフェーズへ分ける

最新対象の選択は日付接頭辞を持つディレクトリだけを名前順で行い、`example/`等を含めない。

## モード2: 実装

1. tasklistの状態が`active`であることを確認する
2. 実装フェーズの先頭の未完了タスクを実装する
3. 完了直後に該当行を`[x]`へ更新する
4. 実装フェーズが完了するまで繰り返す

計画と実装が乖離した場合は、tasklistへ理由を注記し、必要ならdesignも更新する。

## 状態操作

状態変更は`scripts/steering_state.py`を使う。スキルはユーザー意図と記録内容を判断し、スクリプトは許可された遷移と書式を機械的に保証する。

### 中断: `active → paused`

ユーザーが「今日はここまで」「中断する」「別ハーネスへ引き継ぐ」と明示した場合に実行する。

```bash
python3 scripts/steering_state.py pause \
  --harness Codex \
  --completed-scope "完了済みの範囲" \
  --uncommitted-changes "なし、または変更概要" \
  --resume-at "次に再開するタスク" \
  --reason "中断理由"
```

中断記録には、中断日時、使用ハーネス、完了済み範囲、未コミット変更、再開位置、中断理由を残す。通常lintを実行して`paused`と記録の整合性を確認する。

### 再開: `paused → active`

```bash
python3 scripts/steering_state.py resume \
  --harness Codex \
  --resume-at "再開するタスク" \
  --reason "ユーザーの再開依頼"
```

中断記録を読み、requirementsの使用ハーネス欄へ必要な追記をした後、記録された再開位置からモード2を続ける。最終品質ゲート失敗後に`complete`から修正を再開する場合も同じ`resume`操作を使い、理由を記録する。

### 完了: `active → complete`

実装・4段検証・振り返りとドキュメント更新の全チェックボックスが完了した後に実行する。

```bash
python3 scripts/steering_state.py complete --harness Codex
```

未完了、振り返り欠落、プレースホルダー残存があれば遷移は失敗し、tasklistを変更しない。最終品質ゲート、コミット、G3受け入れ記録、push、PRは循環を避けるためtasklistのチェックボックスにせず、add-feature手順が実行管理する。

## モード3: 振り返り

実装フェーズと4段検証フェーズの全項目が完了してから、次を記録する。

- 実装完了日
- 計画と実績の差分
- 追加タスクと技術的スキップ
- 技術面・プロセス面の学び
- 次回への改善提案
- リリース判断

振り返りとドキュメント更新フェーズをすべて`[x]`にし、状態操作の`complete`へ進む。振り返りはdistillの入力になるため、普遍性・再現性・抽象性を意識する。
