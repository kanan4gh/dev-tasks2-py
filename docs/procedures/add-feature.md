# add-feature 手順（機能追加ワークフロー）

新機能を既存パターンに従って実装するワークフローの手順書です。**計画はユーザー承認必須、承認後は完了まで自動実行**(「計画は承認必須・実装は自動」の原則)。ハーネス中立の正であり、各ハーネスの呼び出し口(Claude Codeでは `/add-feature` コマンド)はこの手順書に対応します。ハーネスが専用ツール(作業ツリー分離・調査/計画の委譲・構造化承認UI等)を提供する場合の割当はアダプタ側の定義を参照してください。

**引数**: 機能名(例: 「ユーザープロフィール編集」)

**承認ゲートはステップ4.5の1箇所のみ。** そこまでは調査・計画を進めて承認を求め、承認後はユーザーの介入なしに完了まで実行する。

## ステップ0: 作業の隔離

mainの作業ツリーを汚さないための担保。

1. 関連するGitHub Issueを確認する。存在しない場合は作成し、Issue番号を控える
2. 機能名から**英語 kebab-case のタスク名**を決める(例: 「ユーザープロフィール編集」→ `user-profile-edit`)。ステアリングディレクトリ名にも同じタスク名を使う
3. フィーチャーブランチ `feature/[タスク名]` を作成する。ハーネスが作業ツリー分離(worktree等)を提供する場合は併用を推奨する
4. ブランチ作成に失敗した場合(名前重複等)はユーザーに報告して中断する。自動リネーム等で暗黙に進めない

**mainブランチ上で実装を始めないこと**を必ず守る。

## ステップ1: 準備とコンテキスト設定

1. タスクコンテキストを確立する: 機能名 / 日付(YYYYMMDD) / ステアリングディレクトリパス `.steering/[日付]-[タスク名]/`
2. ステアリングディレクトリを作成する

## ステップ2: プロジェクト理解

1. AGENTS.md(と使用中ハーネスのアダプタ追記)を読み、プロジェクトの全体像を把握する
2. `docs/` の永続ドキュメントを確認し、関連する設計思想やアーキテクチャを理解する

## ステップ3: 既存パターンの調査

対象機能に関連する既存の実装パターン・命名規則・類似コンポーネントを検索・調査する。調査はトークン消費が大きく判断は浅いため、ハーネスが調査の委譲手段(軽量モデルへの委譲等)を提供する場合は委譲を推奨する。結論(発見したパターンの一覧と参照ファイルパス)を設計の入力とする。

## ステップ4: 計画フェーズ

1. 調査結果をもとに実装戦略(ステップごとの作業・変更対象ファイル・アーキテクチャ上のトレードオフ)を立案する。ハーネスが計画の委譲手段を提供する場合は利用してよい
2. **パス判定**: 以下の適用基準を**すべて**満たす場合、軽量パスを選択できる(1つでも満たさなければ通常パス):
   1. 既存パターンの踏襲のみで、新しいアーキテクチャ要素・新規依存を導入しない(例: 新規ライブラリ追加・新規レイヤーや抽象化層の導入・DBスキーマ変更があれば非適用)
   2. 変更対象が3ファイル以下(テスト除く)
   3. **対象文書の更新が不要**。
      - **対象文書**とは次を指す:
        - `AGENTS.md`(SDDプロセス正典)と、各ハーネスアダプタの規範記述(`CLAUDE.md` / `.claude/commands/` / `.agents/skills/` / `.kiro/skills/` 等)
        - AGENTS.md プロダクト固有層が列挙する**永続ドキュメント**
        - `docs/procedures/` の**手順書**と `docs/procedures/templates/` の**テンプレート**
      - **記録例外**: 次の2条件を**ともに**満たす更新は、本基準を満たすものとして扱う。その文書が「何を定めるか」自体は変わらず、設計判断が発生しないためである
        1. **変更の実体が対象文書の外にある**(コード・設定・機構の変更が本体であり、文書の更新はその記録にすぎない)
        2. 文書の更新が、その文書が定める**一覧・台帳の項目の追加・削除・値の更新と、その理由の記述にとどまる**(理由の記述はいずれの場合も必須)
      - **記録例外に該当しないもの**(1つでも当てはまれば通常パス):
        - 文書への記述**そのものが変更の実体**である場合。例: `functional-design.md` の機能一覧へ機能を追加する、`glossary.md` の用語一覧へ用語を追加する。**一覧が設計の実体である文書では、項目追加そのものが設計判断である**
        - 一覧・台帳の**分類体系や適用範囲そのもの**が変わる場合。例: 台帳の分類値を新設する、検査対象の定義を広げる
        - その文書が定める**方針・条件・手順そのもの**を変える場合。例: 除外を追加してよい条件を変える、検証の順序を変える
        - 上記と記録にとどまる更新が**同一の変更に混在する**場合(方針変更を含む以上、非適用)
      - 記録例外を適用した場合は、判定結果(**変更の実体がどこにあるか**、どの文書のどの一覧へ何をしたか)を requirements.md に記録する
   4. データ形式・API契約の破壊的変更がない
3. **G3受け入れの要否判定**: 判定基準は「**ハーネスのアダプタ構成・権限・フックを変更したか**」である(`docs/procedures/derived-project-rollout.md` フェーズ4と同じ基準)。具体的には、スキル・エージェント・コマンドの**定義メタデータ(frontmatter・ファイル名・配置)**、権限設定、フック定義・登録、ハーネス設定ファイルのいずれかを変えた場合、`docs/procedures/harness-acceptance.md` のG3実機受け入れが必要である。
   - **不要**: 手順書・テンプレート・`docs/` の永続ドキュメント・テストのみの変更、および**アダプタ本文の手順記述だけを書き換えた変更**(表示・実読込・承認境界・Stop挙動のいずれも変わらないため)
   - 判定結果(要 / 不要と理由)を requirements.md に記録する。実施はステップ8-Bで行う
4. steering 手順(`docs/procedures/steering.md`)の**モード1**で、ステアリングファイルを作成する
   - **通常パス**: `requirements.md` / `design.md` / `tasklist.md` の3ファイル
   - **軽量パス**: `requirements.md` / `tasklist.md` の2ファイル。requirements.md に「**軽量パス**: 適用」の宣言行を置く。あわせてステップ2-3の読み込み・調査も関連ドキュメント・関連コードに限定してよい
   - **どちらのパスでも**、requirements.md の「パス判定」セクションに**基準4項目それぞれの判定結果**を記録する(通常パスでは満たさなかった基準とその理由、記録例外を使った場合はその内容)
   - tasklist.md のフェーズは、テンプレート(`docs/procedures/templates/tasklist.md`)の「フェーズとステップの対応」に従って**消化するステップごとに排他的に分割する**(実装フェーズ=ステップ5 / 4段検証フェーズ=ステップ6 / 振り返りとドキュメント更新フェーズ=ステップ7)。状態遷移・最終品質ゲート・コミット・G3・PRは手順が管理し、チェックボックスにしない

## ステップ4.5: 計画の承認(このワークフロー唯一の承認ゲート)

1. `design.md`(軽量パスでは `requirements.md`)の要点を計画として提示する: 実装アプローチ / 変更対象ファイル / tasklist.mdのタスク一覧 / 検証方針 / **G3受け入れの要否判定**
2. **パス判定を、選択したパスにかかわらず計画と一緒に提示する**: 基準4項目それぞれの判定結果(満たす / 満たさない と理由)と、結論(通常パス / 軽量パス)を示す
   - **軽量パスを選択した場合**: 4項目すべてを満たす根拠を示す(暗黙に軽量化しない)
   - **通常パスを選択した場合**: **どの基準を満たさなかったか**を示す。これを省くと、基準側に問題があって不要に通常パスへ落ちている状態(=過剰な検証コスト)がユーザーから見えず、基準を改善する機会が失われる
   - **新たな承認ゲートは設けない**。パス判定はこのステップで提示する計画の構成要素であり、計画の承認をもって確認されたものとする(承認ゲートを増やすと「計画は承認必須・実装は自動」の原則を壊す)
3. 選択肢(承認して実装開始/修正を指示する/中止する)を明確に提示して承認を求め、回答を待つ。ハーネスが構造化された承認UI(計画モード・選択式質問等)を提供する場合はそれを優先する
4. **承認された場合**: 以降は無停止で実行する。ただちにステップ5へ
5. **修正を指示された場合**: 指示をステアリングファイルに反映し、再度この承認ゲートを実行する

> **承認待ちと状態**: 作成直後のtasklistは`active`であり、未完了は通常lintで許容される。計画承認を待つために`paused`へ変更しない。各応答の終了は作業状態の変更ではなく、Stopフックによる終了ブロックも使用しない。

## ステップ5: 実装ループ(実装フェーズの完全消化)

**tasklist.mdの実装フェーズの全タスクが `[x]` になるまで繰り返すループ処理。完了したら停止せず、ただちにステップ6へ進む。**

**このループが消化するのは実装フェーズだけである。** 4段検証フェーズ・振り返りとドキュメント更新フェーズのチェックボックスは、それぞれステップ6 / 7が消化する。**これらをステップ5で先行して消化してはならない**(先行消化すると、正式なステップより前に検証・振り返りを実行したことになる)。

1. tasklist.mdを読み込む
2. **実装フェーズに**未完了タスク(`[ ]`)がなければステップ6へ。あれば次へ
3. 実装フェーズの先頭の未完了タスクを1つ特定し、steering 手順の**モード2**で実装する(development-guidelines.md の規約を遵守)
4. 完了したら即座にtasklist.mdの該当行を `[x]` に更新する
5. 1に戻る

> **なぜ「全タスク」ではないのか**: 4段検証と振り返りは後続ステップが実行する。フェーズごとに消化主体を一意にし、後続作業の先取りを防ぐ。

**例外処理**(ループ中に自律的に対処し、ループを継続する):
- **ルールA(タスクが大きすぎる)**: サブタスクに分割してtasklist.mdを更新し、継続する
- **ルールB(技術的理由で不要)**: `- [x] ~~タスク名~~ (理由: ...)` の形式で記録し、継続する
- **エスカレーション(軽量パスの基準逸脱)**: 軽量パスで実装中に適用基準4項目のいずれかを満たさなくなった(4ファイル目の変更が必要になった / 新規アーキテクチャ要素・依存が必要と判明した / **対象文書が定める方針の変更が必要と判明した**(記録にとどまる更新では昇格しない) / 破壊的変更が必要と判明した)場合は、通常パスへ昇格する: design.md を追加作成し、requirements.md の軽量パス欄を「非適用へ昇格(理由)」に更新し、ステップ6は4段フルで実施する。昇格条件はこの4項目の逸脱のみであり、**基準を破ったまま軽量パスで押し切ることを禁止する**
- **禁止**: 「後でやる」による意図的スキップ、理由なき放置、ユーザーへの判断委ね

## ステップ6: 4段検証

**実装フェーズの全タスクが `[x]` になったこと**を確認してから、以下を**段1→段2→(段3・段4は並列可)の順**で実行する。機械的に落ちるものを先に潰し、コストの高いLLM検証を後段に置く。段3・段4は互いに独立しているため並列実行してよい。

**このステップが消化するのは4段検証フェーズのチェックボックスである。** 各段を実行し、その段の指摘対応まで終えた時点で該当行を `[x]` にする(段4の行は、段4の指摘対応が完了した時点で `[x]` にする。段4の実行中に自分自身の行が `[ ]` であるのは正しい状態である)。振り返りとドキュメント更新のフェーズはここでは消化しない。

**再検証は増分方式とする**: 各段の指摘を修正したら、再検証は変更の影響範囲に限定する(該当テスト・該当指摘の解消確認のみ。全段のやり直しはしない)。フル検証はステップ8の最終品質ゲートが決定論的に強制するため、中間のフル再実行は冗長である。

**最終品質ゲートはこのステップでは実行しない**: ステップ7で振り返りとドキュメント更新を行うため、ここでゲートを実行しても最終ファイル状態の検証にならない。ゲートはすべての変更を終えた後の終端ステップ(ステップ8)に置く。

**軽量パスの縮約**: 段1・段2は必須。段3は同一セッションでの変更差分セルフレビューに縮約してよい(独立レビュー原則の意図的な例外。適用基準を満たす小規模差分では、誤り相関のリスクよりプロセスコスト削減を優先する)。段4はスキップできる(スキップした旨と理由をtasklist.mdに記録する)。

### 段1: 静的検証

AGENTS.md技術スタック固有層に定義された検証コマンド(テスト・リント・型チェック)をすべて実行し、パスすることを確認する。

### 段2: 実挙動検証

| 変更種別 | 観察方法 |
|---------|---------|
| 実行可能コード | 実際に起動し入出力を観察する(ハーネスの検証支援機能があれば利用) |
| 手順・定義ファイル(Markdown) | 定義を実データに対して1回実行し、成果物を観察する |
| 純ドキュメント | 観察対象がないため段2をスキップし、その旨をtasklist.mdに記録する |

テスト通過だけで済ませず、必ず実挙動(または成果物)を観察すること。

### 段3: コードレビュー

変更差分のコードレビューを実施する(ハーネスのレビュー支援機能があれば利用)。正当な指摘を修正する(再検証は増分方式に従い、修正の影響範囲に限定する)。

### 段4: スペック準拠検証

`docs/procedures/validate-implementation.md` の手順で、ステアリングファイルと実装の整合性を検証する。`docs/` の永続ドキュメントを変更した場合は `docs/procedures/review-docs.md` のレビューも行う。**いずれも著者と独立した文脈(別セッション・別実行主体)での実行を推奨**(著者の思い込みによる誤り相関を減らすため)。ハーネスが並列の委譲実行を提供する場合は並列化してよい。

スペック乖離は実装を修正するか、意図的な乖離として tasklist.md(必要なら design.md)に理由を記録する。

**完了したら停止せず、ただちにステップ7へ進むこと。**

## ステップ7: 振り返りとドキュメント更新

**このステップが消化するのは振り返りとドキュメント更新フェーズのチェックボックスである。** 各作業を終えた時点で該当行を `[x]` にする。

1. 今回の変更がプロジェクトの基本設計やアーキテクチャに影響する場合、`docs/` の関連する永続ドキュメントを更新する(不要と判断した場合はその判断を記録する)
2. **このステップで `docs/` を更新した場合、その差分はステップ6の段3・段4のレビューを受けていない。** `docs/procedures/review-docs.md` のレビューを更新差分に対して実施し、指摘対応まで終えてから当該チェックボックスを `[x]` にする(ステップ6へ戻らないのは、戻ると振り返り→検証→振り返りの循環が生じるため。レビューをこのステップ内に閉じることで順序を直線に保つ)
3. steering 手順の**モード3**で振り返りをtasklist.mdに記録する
4. 振り返りとドキュメント更新フェーズの全チェックが`[x]`になったことを確認し、`python3 scripts/steering_state.py complete --harness {使用ハーネス}`で状態を`complete`へ変更する。未完了・振り返り欠落・プレースホルダーがあれば遷移は失敗するため、修正して再実行する

**このステップの完了時点で、tasklist.md の全チェックボックスが`[x]`、状態が`complete`になる。**

**完了したら停止せず、ただちにステップ8へ進むこと。**

## ステップ8: 最終品質ゲートとPR作成・後片付け

最終品質ゲート(`scripts/local_quality_gate.py`。実体は技術スタック固有層に定義された単一ゲート)は、実装・4段検証・振り返り・ドキュメント更新をすべて終えた後の**終端ステップ**である。最後の変更より後に実行されなければ最終ファイル状態の検証にならないため、必ずこの位置で実行する。

tasklistに最終品質ゲートのチェックボックスを置かない。ステップ7で全チェックを完了して状態を`complete`へ遷移し、**ゲートの実行は次の8-Aまたは8-Bの分岐内だけで行う**。add-featureは現在のステアリング名を`local_quality_gate.py --steering [ステアリング名]`へ渡し、全履歴の通常規則とPR対象の完了規則を1回のsteering lint走査で評価する。

**ステップ4のG3受け入れ要否判定に従って分岐する**: 判定が「不要」なら**8-A**(既定)、「要」なら**8-B**を実行する。

### ステップ8-A: G3不要の場合(既定)

1. **最終ゲート**: `local_quality_gate.py --steering [現在のステアリング名]`を1回実行して全緑を確認する
2. 失敗した場合は`steering_state.py resume`で`active`へ戻し、影響する4段検証・振り返りを更新して再び`complete`へ遷移する。その後、最終ゲートを改めて1回実行する
3. 全変更をコミットする(Conventional Commits形式。本文に`Closes #[Issue番号]`を含める)
4. ブランチをpushし、PRを作成する(本文: 概要 / 変更理由 / 変更内容 / テスト結果 / 関連Issue)
5. 作業ツリー分離を使用した場合は後片付けする
6. PRのURLをユーザーへ報告する。マージはユーザーの判断に委ねる

### ステップ8-B: G3受け入れが必要な場合

G3(`docs/procedures/harness-acceptance.md`)は「**成功済みローカル品質ゲート**」「**固定commit**」「**使い捨ての複製(clean clone)**」を実施条件とする一方、その結果は記録として残さなければならない。記録を先に書けばゲートの検証対象が古くなり、ゲートを先に回せば記録が検証対象外になる——この循環は、**受け入れ記録が製品ファイルを変更しない**ことを使って直線化する。

以下の順序で実行する。

1. **候補ゲート**: 8-Aの手順1〜2に従い、ローカル品質ゲートを1回で全緑にする
2. **候補コミット**: 全変更をコミットする(Conventional Commits形式。本文に `Closes #[Issue番号]` を含める)。このコミットがG3の**固定commit**になる
3. **G3実施**: 候補コミットを使い捨ての複製(`/private/tmp` 等)へclean cloneし、`docs/procedures/harness-acceptance.md` に従って対話型IDEまたは対話型CLIで受け入れを行う。**従量課金型headless modeを使わない**
4. **結果記録**: 観察結果と証跡を、**複製ではなく元リポジトリ側**のステアリングディレクトリ(`.steering/[日付]-[タスク名]/`)の `acceptance-record.md` に記録する(複製内に作った確認用fixtureステアリングは複製ごと捨てる)。**この記録はtasklist.mdのチェックボックスにしない**(手順書が実行管理する)
5. **最終ゲート**: 同じ明示対象のゲートを1回実行し、記録を含む最終ファイル状態が全緑であることを確認する
6. **記録コミット**: `acceptance-record.md` をコミットする。手順4は製品ファイルを変更しないため、手順3で観察した実機挙動は候補コミットのまま有効である
7. ブランチをpushし、PRを作成する(本文にG3の判定結果を含める)。以降は8-Aの手順5〜6と同じ

**G3が不合格または保留だった場合**: 記録だけを追記して押し切らない。製品ファイルを変更した以上、その変更に対する実機挙動も4段検証の結果も未観察だからである。次の順序で戻る。

1. `steering_state.py resume`で`active`へ戻し、4段検証フェーズのうち修正の影響を受ける段の行を`[ ]`へ戻す
2. **ステップ6の該当段から再実行する**(再検証は増分方式に従い、修正の影響範囲に限定してよい)
3. ステップ7で振り返りに不合格の経緯を追記し、再び`complete`へ遷移して**手順1(候補ゲート)からやり直す**

**状態遷移・最終品質ゲート・コミット・PR作成・G3受け入れ記録はtasklist.mdのチェックボックスにしない**。実行後にしか完了できない手順アクションをゲート対象のチェックボックスにすると自己参照になるため、実行管理は本手順書へ委ねる。
