# 技術仕様書 (Architecture Design Document)

## テクノロジースタック

### 言語・ランタイム

| 技術 | バージョン |
|------|-----------|
| Python | 3.12 以上 |
| uv | 0.11 以上 |

**選定理由**:

- **Python 3.12** — 型ヒントの表現力が高く（`X | Y` 構文、`TypeAlias` 等）、pydantic との親和性に優れる。
- **uv** — Rust 製の高速パッケージマネージャー。`uv sync` 1コマンドで仮想環境の作成から依存インストールまで完結。`uv.lock` で再現性を保証。

## アーキテクチャパターン

### Clean Architecture

TypeScript版と同じ4層構造を採用する。依存は外→内の一方向のみ。

```
┌───────────────────────────────┐
│   CLI レイヤー                 │ ← 入力受付・バリデーション・結果表示
│   src/task_cli/cli/           │   typer + rich (Renderer)
│   （Interface Adapter）        │
├───────────────────────────────┤
│   ユースケース層                │ ← 複数サービスの調整・ストレージパス解決
│   src/task_cli/usecases/      │
│   （Application Service）      │
├───────────────────────────────┤
│   サービスレイヤー               │ ← 個別ドメインロジック
│   src/task_cli/services/      │   TaskManager / GlobalConfigService
│   （Domain Service）           │
├───────────────────────────────┤
│   ストレージレイヤー             │ ← YAML ファイルへの読み書き
│   src/task_cli/storage/       │   FileStorage / GlobalConfigStorage
│   （Infrastructure）           │
└───────────────────────────────┘
         ↓ 外部依存
┌──────────────────┐
│ ~/.task-py/ (FS)    │
└──────────────────┘
```

### データモデル（pydantic）

TypeScript の型定義を pydantic `BaseModel` で表現。バリデーションをモデル層に集約する。

```python
# TypeScript版
type TaskStatus = 'open' | 'in_progress' | 'completed' | 'archived';

# Python版
class TaskStatus(str, Enum):
    OPEN = "open"
    IN_PROGRESS = "in_progress"
    COMPLETED = "completed"
    ARCHIVED = "archived"
```

## データ永続化戦略

### ストレージ方式

| データ種別 | パス | フォーマット |
|-----------|------|------------|
| グローバル設定 | `~/.task-py/config.yaml` | YAML オブジェクト |
| タスクデータ（プロジェクト） | `~/.task-py/projects/<name>/tasks.yaml` | YAML 配列 |
| タスクデータ（Inbox） | `~/.task-py/inbox/tasks.yaml` | YAML 配列 |
| ルーティーン定義 | `~/.task-py/daily/routines.yaml` | YAML 配列 |
| 日別達成ログ（直近30日） | `~/.task-py/daily/log.yaml` | YAML 配列 |
| 実行中タイマー | `~/.task-py/timer.yaml` | YAML オブジェクト |

作業時間の実績（作業セッション）は独立したファイルを持たず、`Task.work_sessions` として `tasks.yaml` に内包する。タスク ID はストレージローカルであり `move` のたびに採番し直されるため、外部ファイルに `(project, task_id)` で持つと move / プロジェクト改名 / 削除のすべてに整合処理が必要になる。タスク自身に持たせればその義務がなくなる。

**プロセス間で共有される状態**: `timer.yaml` は「今どのタイマーが動いているか」というプロジェクト横断の唯一の答えを保持する。残り時間・経過時間は保存された開始時刻から都度導出し、カウントダウンの値を変数として持たない。この設計により、CLI・MCP サーバー・（将来の）ローカル Web GUI がそれぞれ別プロセスであっても同じ状態を読める。プロセスの生死はタイマーの有効性の判定に使わない（PID は再利用されるため信用できない）。

※ TypeScript版は JSON だが、Python版は YAML を採用（pyyaml が標準的なため）。

### 書き込み戦略（不可分な置き換え）

すべての YAML は `storage/atomic.py` の `write_atomic()` を通して書く:

1. **同じディレクトリ**の一時ファイルへ書き出す
2. `flush()` → `os.fsync()` で中身を永続化する
3. `os.replace()` で本体と差し替える
4. 親ディレクトリを `fsync()` して、差し替え自体を永続化する

読み手が観測するのは常に「差し替え前の完全な内容」か「差し替え後の完全な内容」の
どちらかであり、書きかけのファイルは存在しない。書き込みが途中で失敗しても本体は
一切変更されない（従来の `open(path, "w")` は開いた時点でファイルを 0 バイトへ
切り詰めるため、ここで落ちるとデータが失われた）。

一時ファイルを同じディレクトリに作るのは、`os.replace()` が不可分なのは同一
ファイルシステム内だけで、`/tmp` を経由するとその保証が消えるためである。

### バックアップ戦略

`FileStorage.save()`（`tasks.yaml`）だけが `.bak` を持つ:

1. 既存ファイルを `tasks.yaml.bak` にコピー
2. 上記の書き込み戦略で `tasks.yaml` を差し替え
3. 成功したら `.bak` を削除（失敗したら `.bak` を元のパスに移動して復元）

不可分な置き換えを入れた以上、書き込み失敗時の復元は**実質的に何もしない**
（本体は既に無変更のため、`.bak` を戻しても同じ内容を上書きするだけである）。
それでも経路を残しているのは、`.bak` の意味論（書き込み前に作り、成功したら消す）を
利用者から見て変えないためである。

### 排他制御

各ストレージは `transaction()` を公開する。`<対象ファイル>.lock` に対する
`fcntl.flock(LOCK_EX)` で、**`load()` → 変更 → `save()` の全体**を覆う。

`save()` だけを守ってもロストアップデートは防げない。2つのプロセスが同じ時点の
内容を読み、あとから保存したほうが「自分が読んだ時点の一覧全体」を書き戻すため、
もう一方の変更が丸ごと消えるからである。

排他区間の境界を決めるのは、単一ストレージの操作ではservice層
（`TaskManager` / `ProjectService` / `DailyService` / `TimerService`）、複数の
ストレージに跨る操作ではそれを調整するusecase層である（`move` は移動元と移動先の
2ファイルを1つの区間で握るため、`TaskCrudUseCase` が `locked()` を直接使う）。
いずれの場合もstorageは境界の提供だけを担う。

| 性質 | 決定 | 理由 |
|---|---|---|
| ロック対象 | 本体ではなく `<path>.lock` | `os.replace()` で inode が入れ替わると、本体に付けたロックが別のファイルに付いてしまう |
| 残骸の後始末 | **しない** | プロセスが死ねば OS が `flock` を解放する。`.lock` ファイルは残るが中身は空で無害。タイマーで PID を信用しないと決めたのと同じ理由で、プロセスの生死を判定に使わない |
| 再入 | 同一プロセス内では許可 | `move_task` は2ストレージを跨いだ区間を開き、その内側で `save()` が同じロックを取りに行く。`flock` は同一プロセスでも別 fd なら待つため、許さないと自己デッドロックする |
| 複数パスの取得順 | 正規化してソート順 | `move` を A→B と B→A で同時に走らせたときのデッドロックを防ぐ |
| 入れ子の向き | `timer.yaml` → `tasks.yaml` | `stop` はタイマーを読んでから作業セッションをタスク側へ書く。逆向きは作らない |
| タイムアウト | 設けない | 単一利用者のローカル操作は数ミリ秒で終わる |
| `fcntl` の無い環境 | ロックなしに縮退 | 現行と同じ強度であり後退しない |

**残る窓**: `project rename` は `config.yaml` のロックの内側でディレクトリ移動まで
行うが、移動対象の `tasks.yaml` 自体のロックは取らない。改名の最中に別プロセスが
旧名のプロジェクトへ書き込むと、その書き込みは移動後の旧ディレクトリに取り残される。
閉じるにはプロジェクト単位の上位ロックが要り、単一利用者の想定に対して機構が重い。

### ファイルパーミッション

| パス | パーミッション |
|-----|-------------|
| `~/.task-py/` および配下ディレクトリ | `700`（オーナーのみアクセス可） |
| `tasks.yaml`, `config.yaml` 等（新規作成時） | `600` |
| 既存ファイルの置き換え | 元のパーミッションを引き継ぐ |
| `<対象ファイル>.lock` | `600` |

新規作成が `600` なのは、一時ファイル（`tempfile.mkstemp` 由来）のパーミッションを
そのまま使うためである。umask を読むには `os.umask()` で一度書き換えて戻す必要が
あり、スレッドを持つローカル Web サーバーでは競合する。`600` は従来の `644` より
狭く、親ディレクトリが `700` である以上、単一利用者の運用に影響しない。

## テスト戦略

### ユニットテスト（pytest）

- **対象**: `models/`（バリデーション・ステータス遷移）、`storage/`（読み書き・バックアップ）、`services/`（CRUD・ステータス遷移・検索）、`usecases/`（ライフサイクル・エラーケース）
- **方針**: `tmp_path` フィクスチャで実ファイルシステムを使用。ストレージモックは最小限。
- **カバレッジ目標**: 全体 80% 以上

### テスト実行

```bash
uv run pytest                    # 全テスト
uv run pytest --cov=src          # カバレッジ付き
uv run pyright src tests         # 型チェック
```
